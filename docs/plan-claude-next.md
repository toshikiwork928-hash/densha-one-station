# 高野線の拡張の計画（未着手）

作成 2026-10-09、更新 2026-11-04。対象は `apps/densha-one-station`。
2026-10-09 の計画のうち、南海本線の南部コース（泉佐野〜和歌山港）、コース別の読み込み、標準・イラストの切替の軽量化、泉佐野の駅舎は実装済みなので消した。残りは高野線なんば〜堺東と、泉北線・高野線の車両。
最初に読むもの: リポジトリの `AGENTS.md`、[ROADMAP.md](../ROADMAP.md)、[handover.md](./handover.md)（8章 Pages の手順、9章 ユーザーの指定）。

## 1. 高野線なんば〜堺東

約11.0km、12駅を上下方向で設計する。駅順は、なんば・今宮戎・新今宮・萩ノ茶屋・天下茶屋・岸里玉出・帝塚山・住吉東・沢ノ町・我孫子前・浅香山・堺東。

なんば〜岸里玉出は既存の本線コースで描画している高野線の線路・駅を調べ、共有できる地形と構造物を使う。走行用の駅位置、進路、停止位置、信号、速度制限は高野線用に定義する。既存の描画用 `world/koya-traffic.ts` を、そのまま自列車の運行データにはしない。

操作車両はまず8300系・6300系。車両形式を理由に選択可能な種別を増やさず、最新の公式停車駅で各停・準急・区間急行・急行の設定と選択可否を決める。優等列車が通過する駅を出発・到着駅として選ばせない。端点のなんば・堺東の番線、車止め、ホーム長、折返し、ドア側を上下で確認する。

堺東の配線と待避、住吉東などの構内、浅香山付近の橋、曲線と駅間距離を先に調査する。実際の各種別の所要時間は未確定。公式時刻表の基準列車を示したうえで、自動運転からゲームのダイヤを生成する。

対向列車は高野線系統の時刻表を取得する。本線の列車番号・本数を流用しない。既存の共通処理に路線別データを渡し、画面外でも運行、先行列車の最後尾から300m以上、ホーム・合流進路の占有確認を維持する。既存の高野線モブと同じ列車を二重に表示しない。

候補パスは `src/route/routes/`、コース登録・選択処理、`src/world/koya-traffic.ts`、共通駅生成、対向ダイヤ生成スクリプトとデータ、路線検証スクリプト。具体的な新規ファイル名と共有部分の変更範囲は調査後に提示する。

## 2. 泉北線・高野線の車両データ

- 9300系は既存8300系のモデルを基に、泉北の配色・前面表示など必要な差を追加する。外形が完全に同一と断定せず、公式資料で差を確認する。
- 5000系は前面・窓・帯など特徴を確認し、既存モデルの単純な色変更で済むかを判断する。
- 6200系は高野線車両として追加する。編成・配色・外観を確認して車両データと表示を作る。

今回の追加は車両データと表示が中心。操作対象は8300系・6300系だけ。9300系・5000系・6200系を操作車両にするための性能・音・UI追加は別途指示を待つ。対向表示に使う場合も、実際の運用と両数を調べ、形式と種別を混同しない。

候補パスは既存の車両定義、`src/world/` 内の車両モデル、編成生成と対向車両選択。既存形式の外観・性能に影響しないことを確認する。

参考 https://www.nankai.co.jp/library/groupinfo/news/pdf/221111_1.pdf

## 3. 既存の運行仕様を維持する

- 和歌山市方面の急行は春木通過。空港急行は春木停車。
- 羽衣・泉大津発着で通過種別の特急を選ばせない。ボタン、キーボード、ゲームパッド、保存復元は `selectableServices` の共通判定を使う。
- TOPで選べない種別も、実際の対向・待避・通過に必要ならデータを残す。
- 対向列車の本数と発車は実ダイヤを基準とし、自列車の位置・種別で変えない。表示範囲外の列車も運行する。
- 原ダイヤは分単位の発車時刻。到着時刻や実信号位置は推定を含む。ゲームの300m間隔は実閉そくの再現ではない。
- 自列車側の既存待避・待ち合わせ・接続を、駅舎や読み込み変更に合わせて無断で変更しない。

対向ダイヤの出典は https://unyohub.2pd.jp/railroad_nankai/ 。現在の収録元は2024-12-21改正。新コース追加時に最新の対象路線・平日時刻表を確認し、出典と改正日を記録する。

## 4. 検証とPages更新

実装前に変更範囲に応じた検証計画を示す。型・ビルドは `npm run typecheck` と `npm run build`。運行・選択・進路変更は `npm run verify:routes` と `npm run verify:oncoming`。景観・駅舎変更は `npm run verify:clearance`、LOD変更は `npm run verify:scenery`。必要な検証を通した後、同じ検証を理由なく繰り返さない。

新コースでは上下・全選択可能種別・全4時間帯を確認する。新しい配線・番線・ドア側・待避・対向列車の重なりを数値と画面で確認する。読み込み変更では直接起動、上下・通し切替、連続再開始、読み込み失敗、見た目の連続切替、旧コースへの戻りを確認する。メモリーが切替ごとに増え続けないことも測る。

前回はCodexのブラウザー操作が自動承認審査で拒否され、ユーザーの手動画面確認を受けた。自動検証だけで画面確認済みとは報告しない。Claude側で画面を確認できない場合は、その制限と未確認箇所を明示する。

追加・修正作業は検証、画面確認、Pages更新、公開結果確認までが1セット。commit・pushはユーザーの明示承認を確認して行う。本体masterの承認された差分だけを公開用リポジトリへ反映し、両方をビルドする。公開用mainへpush後、Actions成功、公開JSと追加チャンクの取得、実際の公開画面を確認する。完了報告には公開URLと検証結果、未確認事項を短く記載する。
