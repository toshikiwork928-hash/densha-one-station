## 3. 高野線なんば〜堺東

約11.0km、12駅を上下方向で設計する。駅順は、なんば・今宮戎・新今宮・萩ノ茶屋・天下茶屋・岸里玉出・帝塚山・住吉東・沢ノ町・我孫子前・浅香山・堺東。

なんば〜岸里玉出は既存の本線コースで描画している高野線の線路・駅を調べ、共有できる地形と構造物を使う。走行用の駅位置、進路、停止位置、信号、速度制限は高野線用に定義する。既存の描画用 `world/koya-traffic.ts` を、そのまま自列車の運行データにはしない。

操作車両はまず8300系・6300系。車両形式を理由に選択可能な種別を増やさず、最新の公式停車駅で各停・準急・区間急行・急行の設定と選択可否を決める。優等列車が通過する駅を出発・到着駅として選ばせない。端点のなんば・堺東の番線、車止め、ホーム長、折返し、ドア側を上下で確認する。

堺東の配線と待避、住吉東などの構内、浅香山付近の橋、曲線と駅間距離を先に調査する。実際の各種別の所要時間は未確定。公式時刻表の基準列車を示したうえで、自動運転からゲームのダイヤを生成する。

対向列車は高野線系統の時刻表を取得する。本線の列車番号・本数を流用しない。既存の共通処理に路線別データを渡し、画面外でも運行、先行列車の最後尾から300m以上、ホーム・合流進路の占有確認を維持する。既存の高野線モブと同じ列車を二重に表示しない。

候補パスは `src/route/routes/`、コース登録・選択処理、`src/world/koya-traffic.ts`、共通駅生成、対向ダイヤ生成スクリプトとデータ、路線検証スクリプト。具体的な新規ファイル名と共有部分の変更範囲は調査後に提示する。

## 6. コース別読み込みと生成

現在は `src/world/osm-town.ts` が複数区間のJSONを静的importしている。配置する景観は選択コースで絞るが、他区間のデータも初期JSに含まれる。建物の表示範囲を絞るだけでは、読み込み量や生成済みオブジェクトのメモリー使用量は減らない。

選択コースに必要な区間だけ非同期で読み込む。上下は同じ元データを共有し、堺〜岸和田通しは堺〜泉大津と泉大津〜岸和田の2区間を使う。区間をまたぐ待避線・ランドマークを欠落させない。Viteのdynamic import等でファイルを分け、ゲーム開始は必要データの準備完了後に行う。

読み込み中のコース変更で古い処理が新コースに配置しないようにする。失敗時は失敗内容と再試行を表示する。キャッシュを無制限に増やさず、共有素材とコース専用のgeometry・material・textureを区別して解放する。既存のチャンク表示・LODを活用し、遠方の詳細生成も必要時に行う。

候補は `src/world/osm-town.ts`、その呼出元、ワールド初期化、`src/main.ts` と素材準備処理。実際の呼出関係を調べて変更パスを確定する。Pagesのサブパスから追加チャンクを取得できることを公開環境でも確認する。

## 7. 標準・イラスト切替を維持して軽量化する

現状は2つの世界を同時に生成しているわけではない。車両・景観は共有する。ただし `src/render/illustrated.ts` は標準でも接続され、輪郭用geometryの生成、シーンの定期走査、追加shader処理が残る。切替ボタンを消すだけでは十分な軽量化にならない。

推奨は両方を残し、標準ではイラスト専用の処理を開始しない構成。最初にイラストを選んだ時だけコードと輪郭を生成する。毎秒の全シーン走査は、車両・景観の生成時に対象を登録する方式へ変更できるか調べる。標準へ戻した時のshader、露出、霧、材質の復元を明確にする。

切替を繰り返して輪郭やshaderのコールバックが増えないこと、新しく出現する対向車両も現在の見た目に従うことを確認する。夜間、天候、トンネル、信号、透明材質、ドアを確認する。URLの `look=standard` と保存・切替の仕様を維持する。

候補は `src/render/illustrated.ts`、`src/main.ts`、対象モデル生成時の登録処理。ユーザーは描画方式の一本化を指示していない。標準かイラストの削除は行わない。

改善前後は同一端末・同一画質・同一コース・同一視点で測る。なんば、堺〜岸和田通し、岸和田〜泉佐野を比較し、初回取得量、開始までの時間、フレーム時間、描画回数、三角形数、geometry・texture数を記録する。未計測のFPS向上率や容量削減率を約束しない。

## 8. 泉佐野の駅舎・プラットホーム構成

目標は、ホーム・上屋・壁・高架下の駅舎が一体に見える構造。完全な寸法再現ではなく、運転台と俯瞰で泉佐野と分かる形を再現する。

公式構内図ではホーム階3F、改札階2F、地上階1F、東西出口、1〜6番を確認できる。図は2013年版で、改良工事による差異の注記がある。最新の外観写真と照合してから断面・開口部・配色を決める。

（2026-10-09 更新）`src/route/routes/izumisano.ts` は島式3面4線（1/2・3/4・5/6）を定義する。下りは普通・空港系統が外側下り線の1番、急行・サザンが下り本線の2番、上りは本線系統が上り本線の5番、空港系統が外側上り線の6番。出典で種別ごとの番線は確定できないため、ゲーム用の割り当て。詳細は `izumisano-station-reference.md` 5章。以下は更新前の説明。更新前は3面5線で、下りの普通1番、急行・サザン2番、空港方面3番、上り本線5番・空港方面6番だった。公式図・写真でホームの組合せと線路の共有関係を再確認する。ユーザーの「4番線停車確認」だけで番線対応が正しいと判断せず、HUDの表示・停止した線路・対向車の位置を照合する。

現状の建築はcustomの島式ホーム標準上屋と、高架下の簡易箱が中心。駅の3層構造と外観を十分に表していない。

実装案

1. 参考写真の撮影時期と視点を記録し、東西外観、屋根断面、壁・窓、柱、ホーム間の開口部を確認する。全面を閉じたホールかどうかは未確定。新今宮等の形をそのまま移植しない。
2. `src/world/station-architecture.ts` の既存 `hall` と寸法設定を使えるか調べ、泉佐野専用の屋根・外周壁・柱を定義する。開放部分は実物に合わせて残す。
3. `src/world/custom-stations.ts` の既存hall生成経路を利用する。簡易高架下箱と新駅舎を二重に置かず、改札階を示す帯・窓・東西入口を低いポリゴン数で表す。
4. 各ホームの上屋、柱、階段を駅舎全体とそろえる。必要な構造を残しつつ、重複する屋根・壁を避ける。夜間照明と運転台からの視界も確認する。

線路・停止位置・空港分岐・ドア側・45km/hの分岐器制限は建築変更から切り離す。実配線との差が判明した場合は、理由・進路への影響・予定差分を別途提示して承認を得る。既存の終着挙動も、屋根追加を理由に変更しない。

候補パスは `src/world/station-architecture.ts`、`src/world/custom-stations.ts`、必要なら共通ホーム生成と照明処理。配線変更が必要な場合だけ `src/route/routes/izumisano.ts` を別の承認対象とする。

確認する画面は上下方向の各選択可能種別、運転台・俯瞰・全景、標準・イラスト、昼・夜。ホームに車体や柱が重ならないこと、全車の台車が線路上にあること、屋根と架線が干渉しないこと、停止時のドア側、接近時の番線表示、空港側進路を確認する。

## 9. 既存の運行仕様を維持する

- 和歌山市方面の急行は春木通過。空港急行は春木停車。
- 羽衣・泉大津発着で通過種別の特急を選ばせない。ボタン、キーボード、ゲームパッド、保存復元は `selectableServices` の共通判定を使う。
- TOPで選べない種別も、実際の対向・待避・通過に必要ならデータを残す。
- 対向列車の本数と発車は実ダイヤを基準とし、自列車の位置・種別で変えない。表示範囲外の列車も運行する。
- 原ダイヤは分単位の発車時刻。到着時刻や実信号位置は推定を含む。ゲームの300m間隔は実閉そくの再現ではない。
- 自列車側の既存待避・待ち合わせ・接続を、駅舎や読み込み変更に合わせて無断で変更しない。

対向ダイヤの出典は https://unyohub.2pd.jp/railroad_nankai/ 。現在の収録元は2024-12-21改正。新コース追加時に最新の対象路線・平日時刻表を確認し、出典と改正日を記録する。

## 10. 検証とPages更新

実装前に変更範囲に応じた検証計画を示す。型・ビルドは `npm run typecheck` と `npm run build`。運行・選択・進路変更は `npm run verify:routes` と `npm run verify:oncoming`。景観・駅舎変更は `npm run verify:clearance`、LOD変更は `npm run verify:scenery`。必要な検証を通した後、同じ検証を理由なく繰り返さない。

新コースでは上下・全選択可能種別・全4時間帯を確認する。新しい配線・番線・ドア側・待避・対向列車の重なりを数値と画面で確認する。読み込み変更では直接起動、上下・通し切替、連続再開始、読み込み失敗、見た目の連続切替、旧コースへの戻りを確認する。メモリーが切替ごとに増え続けないことも測る。

前回はCodexのブラウザー操作が自動承認審査で拒否され、ユーザーの手動画面確認を受けた。自動検証だけで画面確認済みとは報告しない。Claude側で画面を確認できない場合は、その制限と未確認箇所を明示する。

追加・修正作業は検証、画面確認、Pages更新、公開結果確認までが1セット。commit・pushはユーザーの明示承認を確認して行う。本体masterの承認された差分だけを公開用リポジトリへ反映し、両方をビルドする。公開用mainへpush後、Actions成功、公開JSと追加チャンクの取得、実際の公開画面を確認する。完了報告には公開URLと検証結果、未確認事項を短く記載する。

このPlan作成だけを理由にPagesを更新しない。
