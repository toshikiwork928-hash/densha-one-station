# 実ダイヤの自列車化 調査資料

作成日 2026-11-04。実装はしていない。別の LLM が、自列車を実際のダイヤの1本として走らせる実装に使うための資料。

## 0. 結論

- 全14コース・全時間帯・選べる全種別の実際の列車を `docs/real-timetable/*.json` に抽出した。代表の1本の案、ゲームの時刻表との比較も入っている。
- 自列車側の情報は Hub の原データ（`node_modules/.cache/unyohub/timetable.json`）にそろっている。`src/data/oncoming-timetable.json` は対向列車だけで、自列車の時刻表の元には向かない（1.3）。
- 実ダイヤに無い組み合わせがある。日中の急行（全コース）、朝の下りと夜の上りのラピートβ、みさき公園〜和歌山港の急行・サザンの通し（和歌山港発着は1日3〜4本）。実装では選べなくするか、別の扱いが要る（7.2）。
- 普通の待避の駅は、ゲームの day-patterns と実ダイヤでかなり違う。実ダイヤでは、普通はコースの両端（堺・泉大津・岸和田・泉佐野）で優等を待つことが多い。day-patterns はユーザー指定で「変更しないこと」とされている。変えるならユーザーの確認が要る。
- ゲームの所要時間を実際の到着の推定と比べると、優等（急行・サザン・ラピート）はゲームが0.5〜3分（1〜2割）短い。普通はコースによって長いことも短いこともある（5章）。
- 分からないこと: 途中駅の到着時刻、秒、停車時間、公式時刻表との一致、2024-12-21 より新しい改正の有無（6章）。

## 1. 出典とデータ

### 1.1 出典

- 鉄道運用Hub 南海電鉄 https://unyohub.2pd.jp/railroad_nankai/ の時刻表データ。平日、改正 2024-12-21。API は `timetable.php`（railroad_id=nankai、diagram_revision=2024-12-21、timetable_id=weekday）。運用表データは CC BY 4.0（Hub の表記）。
- 取得は `scripts/oncoming-meets.ts` が以前に行い、`node_modules/.cache/unyohub/` に保存してある（取得日 2026-10-09）。今回はネットに取りに行かず、このキャッシュを読んだ。
- 南海の公式時刻表は今回も取得していない。Hub と公式の照合は未実施。`docs/south-timetable-research.md` 1章でも公式は読めなかったと書かれている。
- ゲーム側の値は、`src/route` の `ROUTES` に `applyService` を時間帯ごとに当てて読んだ（`*-timetable.ts`、`day-patterns.ts` の反映後）。

### 1.2 Hub の時刻の性質

- 分単位。秒は無い。
- 各駅の値は発車時刻。線の終点の値だけが到着時刻。途中駅の到着時刻は無い。
- 通過駅はほぼ null。一部だけ `|HH:MM` で通過時刻がある。
- 24時を過ぎた時刻は `24:08` のように書かれている（深夜の `-急行-` 2401 など）。
- 空港線・和歌山港線・加太線との直通は、列車番号の `next_trains` / `previous_trains` でつながる。
  - 泉佐野の下り空港線直通: 本線の値は泉佐野の到着、空港線の最初の値が泉佐野の発車。102本すべてで違う（1分が92本、2〜3分が9本、8分が1本）。抽出では `arr` と `dep` の両方を入れた。
  - 和歌山市の和歌山港線直通: 本線の値と和歌山港線の値が同じ分。到着と発車の区別はつかない。
- 列車番号の頭の数字で種別がほぼ分かる（例 68xx・65xx・67xx 普通、17xx・19xx 急行、21xx 空港急行、05xx・06xx サザン、02xx ラピートβ、07xx ラピートα）。Hub の値をそのまま使った。番号の付け方の規則は調べていない。

### 1.3 oncoming-timetable.json との関係

- `routes[コースid]` には、そのコースと逆向きの列車だけが入っている（対向列車用）。例えば `routes.shiokaze`（泉大津→堺）の列車は堺→泉大津に走る列車。
- 収録範囲は、各開始時刻の10分前から、その時間帯の最長コース所要時間 +10分まで（handover.md 6章）。代表列車の前後の候補が欠けることがある。
- 位置は逆向きのコースの s（m）、時刻は0時からの発車秒。到着は無い。
- 同じ Hub のデータなので、列車番号・時刻は今回の JSON と一致する。自列車の時刻表は今回の JSON（または Hub の原データ）から作り、対向列車は今の `oncoming-timetable.json` のまま使う形がそろえやすい。

## 2. 作ったデータ

`docs/real-timetable/` の下。コースごとに1ファイル（`<コースid>.json`）と、一覧の `index.json`。

各コースのファイルの中身
- `source` `license` `revision` `fieldNotes`: 出典と項目の説明。
- `stations`: コースの駅（ゲームの並び）。
- `selectableServices`: ゲームで選べる種別、ゲームの停車駅、ゲームの行先。
- `timeOfDay.<morning|noon|evening|night>`
  - `startClock`: ゲームの開始時刻。
  - `window`: 一覧に入れた時間の範囲。コースの最初の駅の時刻が、開始時刻の前後60分にある列車。
  - `pattern`: 種別ごとの本数（`count`、1時間あたり `perHour`）、コースの始発駅の時刻の並び、行先の内訳、停車駅の並びの内訳。加太線直通・和歌山港線内だけの普通は別の種別として数えた。
  - `waitSummary`: 普通・区急が何に、どこで抜かれるかの集計（2.1）。
  - `representatives`: 種別ごとの代表の1本（4章）。ゲームとの比較 `vsGame` 付き。
  - `trains`: 範囲内の全列車。列車番号、Hub の種別名、ゲームの種別 id（`service`。区急・準急・ラピートα・`-急行-` は null）、始発駅・行先、コース内の各駅の時刻、ゲームとの停車駅の違い（`stopsVsGame`）、抜かれ（`overtakenBy`）。

駅の時刻の書き方
- `{"st":"湊","dep":"07:34"}` 発車。
- `{"st":"泉佐野","arr":"07:47","dep":"07:49"}` 到着と発車が別にある（泉佐野・和歌山市の線の境だけ）。
- `{"st":"石津川","pass":null}` 通過、時刻不明。`"pass":"09:44"` は通過時刻あり。

### 2.1 抜かれ（待避・緩急接続）の推定方法

Hub に到着時刻が無いので、次の方法で推定した。推定であり、確定ではない。

1. 同じ向きで格が上の列車（普通 < 区急・準急 < 急行・空港急行 < サザン・ラピート）と、両方に時刻がある駅で発車順を比べる。順が入れ替わったら、その間で抜かれた。
2. 格上の列車の、時刻の無い通過駅の時刻を、前後の時刻とゲームの駅位置（営業キロ相当）で補間する。
3. 普通がその駅にいる時間（到着 = 前の駅の発車 + その駅間の普通の終日最短、から発車まで）に格上の列車が通る駅を、抜かれた駅とする。格上の列車がその駅に停まれば緩急接続、停まらなければ通過待ち。
4. 当てはまる駅が無く、区間が岸里玉出〜住ノ江（本線の4線区間）なら走行中の追い越し。それ以外は「不明」。
5. `extraMin` は、前の駅からその駅の発車までが、普通の終日最短より何分長いか。待ちの長さの目安。

注意
- コースの始発駅・終着駅での待ちも出る（`atCourseOrigin` `atCourseEnd`）。ゲームは始発駅の待避をせず、終着駅の待避は放送だけ（day-patterns.ts の冒頭）。
- 4線区間で、普通が駅に停まっている間に隣の線を抜かれた場合は「通過待ち（推定。長い停車が見えない）」と出る。実際は待っていない。
- 同じ分に発車する2本は順が決まらないので、入れ替わりとして数えない。

## 3. 時間帯ごとのパターン

本数は `pattern.perHour`（コースの最初の駅の時刻が開始時刻の前後60分）。詳しくは各 JSON。ここでは要点だけ書く。

### 3.1 種別の走る時間帯（全線共通）

- 急行。下りは難波発 05:40〜08:22 と 17:16〜21:22。上りは難波着 06:51〜09:50 と 17:54〜21:50。10〜16時台は走らない。
- ラピートβ（堺・岸和田に停車）。下りは難波発 10:35〜22:00（日中は毎時1本、16:30から毎時2本）。上りは難波着 07:39〜20:14。
- ラピートα（堺・岸和田を通過）。下りは難波発 06:00〜16:00、上りは難波着 11:43〜23:34。ゲームの特急ラピートβの停車駅と合わないので、自列車の候補にしていない。
- サザン。終日、毎時2本前後。
- 空港急行。終日、毎時3〜4.5本。
- 区急・準急はゲームに種別が無い。区急は朝・夕・夜にある。準急は朝の上り2本だけ。

### 3.2 堺〜なんば（namba 上り、namba-up 下り）

- 普通は毎時4.5〜6.5本。下りの行先は和歌山市が多く、羽倉崎・みさき公園・樽井・関西空港もある（夕・夜は特にばらつく）。上りは全部なんば行。
- 上り（堺→なんば）の普通は、堺で急行系・特急に抜かれる（緩急接続）のがほとんど。コース内では岸里玉出・粉浜・住吉大社あたりで抜かれるが、多くは4線区間で隣の線を抜かれるだけ。
- 下り（なんば→堺）の普通は、堺で抜かれる（終着駅）。夕は住ノ江で急行系・特急に抜かれる例が多い（8本）。
- ゲームの day-patterns は、なんば〜堺の待避を朝の堺1番線（下り）以外に持っていない。

### 3.3 堺〜泉大津（shiokaze 上り、shiokaze-up 下り）

- 普通は毎時4.5〜6.5本。
- 下り（堺→泉大津）
  - 朝。堺で急行系に接続、浜寺公園で急行系・特急に通過待ち、高石で通過待ち、泉大津で空港急行に接続。
  - 日中。堺で空港急行・サザンに接続、高石で特急の通過待ち（ラピートα。前後2時間で2本）、泉大津で空港急行に接続・特急の通過待ち。
  - 夕。浜寺公園で急行系・特急・区急の通過待ちが多い。泉大津で接続。
  - 夜。浜寺公園で急行系・特急の通過待ち、堺と泉大津で接続。
- 上り（泉大津→堺）
  - 朝。泉大津で急行に接続、浜寺公園で急行系・特急の通過待ち（10本・5本）、堺で接続。
  - 日中。泉大津で空港急行に接続・特急の通過待ち、高石で特急の通過待ち（3本）、堺で接続。
  - 夕。高石で特急の通過待ち（6本）、泉大津・堺で接続。
  - 夜。泉大津で接続、高石・浜寺公園で通過待ち、堺で接続。

### 3.4 泉大津〜岸和田（kishiwada 下り、kishiwada-up 上り）

- 普通は毎時4.5〜6.5本。コースの途中（忠岡・春木・和泉大宮）での抜かれはほぼ無い。抜かれるのは両端の泉大津と岸和田。
- 上り（岸和田→泉大津）の朝は、停車駅が5駅でない普通・準急がある（3駅、`stopPatterns` 参照）。

### 3.5 堺〜岸和田の通し（nankai-through 上り、nankai-through-up 下り）

- 3.3 と 3.4 を合わせた形。泉大津で接続・通過待ちする普通が多い。

### 3.6 岸和田〜泉佐野（izumisano 下り、izumisano-up 上り）

- 普通は毎時4.5〜6本。
- 下りの普通は、泉佐野（終着駅）で空港急行・サザンに抜かれる（緩急接続）のがほとんど。貝塚での抜かれもある（日中2本、夜4本など）。
- 上りの普通は、泉佐野（始発駅）でサザンを待ってから出る（日中4本）。`south-timetable-research.md` 5章で不明だった、上りの普通が泉佐野で長く停まる理由と読める（推定）。

### 3.7 泉佐野〜みさき公園（izumisano-misaki 下り、-up 上り）

- 普通は毎時4〜6.5本。日中の下りは、羽倉崎止まり（泉佐野〜羽倉崎の2駅だけ）が毎時2本ある。
- 急行は朝2本/時、夕1本/時、夜1.5本/時。日中は無い。サザンは毎時2本（朝の下りは1本/時）。
- 下りの普通は尾崎で急行系・サザンに接続する。日中は、ゲームの開始時刻の前後（9〜11時）では尾崎で待つ普通がほとんど無い（11時台から毎時2本。research 5章）。
- 上りの普通は朝に尾崎で急行に接続（6本）、夜はサザンに接続（4本）。

### 3.8 みさき公園〜和歌山港（misaki-wakayamako 下り、-up 上り）

- 本線の普通（みさき公園〜和歌山市）は毎時3〜4.5本。このほか加太線直通の普通（和歌山市〜紀ノ川だけ本線）が毎時2.5〜3.5本、和歌山港線内だけの普通（和歌山市〜和歌山港）が朝・夕に数本。
- 本線の普通で、みさき公園から和歌山港まで行く列車は無い。ゲームの普通の通しも和歌山市まで（`partialGoals`）。
- 和歌山港まで行く急行・サザンは1日に急行3本・サザン3本（上りは急行4本・サザン3本）。時刻は research 6章。
- コース内の抜かれは、ほぼ無い（朝の和歌山大学前の接続1本、日中の孝子の通過待ち1本）。

## 4. 代表の1本の案

選び方（`representatives` の `reason`）
- そのコースの始発駅で停車して発車し、終着駅に停車する、その種別の列車。
- コースの始発駅の発車が開始時刻に最も近いもの。同じ差なら後の列車。
- 前後60分に無いときは、終日で最も近い列車を `inWindow: false` で入れた。自列車には向かない。
- みさき公園〜和歌山港は、急行・サザンについて、和歌山港まで（`express` `southern`）と、和歌山市まで・和歌山市から（`express@和歌山市まで` など）の2通りを選んだ。普通は和歌山市まで・和歌山市からだけ。
- 前後の候補を `prevCandidate` `nextCandidate` に入れた。開始時刻を少しずらす実装なら、そちらも使える。

## 7. 実装する LLM への申し送り

方針は案。決めるのはユーザー。

### 7.1 データの置き場所の案

- 案A: 種別×時間帯ごとの実際の時刻を `ServiceSpec.timetableByTime` に入れる。いまの `timetableByTime`（普通だけ、scripts/timetable.ts が生成）と同じ形 `{駅index: {arr, dep}}` で、秒。0 をコース始発駅の発車にそろえる。
  - 開始時刻は時間帯で固定（`START_CLOCK`）なので、`route.startClock` を代表列車のコース始発駅の発車時刻（秒）に変える必要がある。いまは `syncClock`（game/loop.ts）が `START_CLOCK[tod]` を入れている。
  - 対向列車は `route.startClock + state.t` で動くので、startClock を実際の発車時刻にすれば、対向列車との位置関係が実ダイヤに合う。
- 案B: 列車ごとの時刻（列車番号つき）を別のデータ（例 `src/data/player-timetable.json`）に置き、種別・時間帯から列車を引く。行先・列車番号も一緒に持てる。生成は `scripts/oncoming-meets.ts` と同じ Hub のキャッシュから作るスクリプトを足す形が自然。
- どちらでも、到着時刻は Hub に無い。到着 = 発車 − 停車時間（ゲームの25秒など）とするか、前の駅の発車 + 走行時間で作るかを決める必要がある。scripts/timetable.ts の `REAL_FLOORS`（泉佐野以南だけ、Hub の中央値の下限）が今の近い仕組み。

### 7.2 注意点

- ゲームの列車は実際より速く走れる。ゲームの時刻表は自動運転の最速 +5% で、優等は実際より0.5〜3分短い。実ダイヤの時刻にすると、余裕（早着）が出る。定時の判定・評価の基準が変わる。
- 分単位の誤差。Hub は分の切り捨てか四捨五入か不明。到着・発車を秒で決めるときは±30秒の幅がある。
- 深夜。24時を過ぎた時刻は `24:xx`。開始時刻 21:30 の夜は、代表列車が0時をまたがないので、今は問題にならない。ゲームの時計（0時からの秒）が86400を超える場合の表示は確かめていない。
- 日中の急行。実ダイヤに無い。選択肢から外すか、日中だけ別の時刻（直前の朝の列車、または今の自動生成）を使うかを決める。ラピートβの朝の下り・夜の上りも同じ。
- みさき公園〜和歌山港の通しの急行・サザン。1日数本で、開始時刻から離れる。和歌山市まで・和歌山市からの区間（`partialGoals`）の代表を使う案がある。
- 区間（stage）を選んだ場合。stage の始発駅の発車時刻は、同じ列車の、その駅の発車時刻を使えばよい（JSON の `times`）。代表をコースの始発駅で選んでいるので、stage ごとに選び直すかは決める。
- 待避の再現。実際の待ちはコースの両端（堺・泉大津・岸和田・泉佐野）に多い。ゲームは始発駅の待避をせず、終着駅は放送だけ。始発駅で待つ普通を自列車にすると、発車が遅れる形になる（発車時刻をそのまま実ダイヤにすれば、待ちは時刻表の中に入る）。
- day-patterns.ts はユーザー指定で、変更しないこととされている（handover.md 6章）。実ダイヤに合わせて待避の駅を変えるなら、先にユーザーに確認する。
- 自列車を抜く列車・先行列車（game/overtake.ts、game/preceding.ts）はゲームの仮想列車。自列車を実際の1本にするなら、同じ向きの前後の実際の列車（JSON の `trains`、`overtakenBy` の `by`）と合わせるかが次の課題になる。
- 対向列車の時刻表（oncoming-timetable.json）は、いまの開始時刻を基準に収録範囲が決まっている。startClock を変えると収録範囲の外に出る場合がある。範囲を広げて再生成する（`npm run oncoming:meets -- --timetable`）必要があるか確かめる。
- 同じ列車番号が2本ある可能性は確かめた範囲では無い（Hub の honsen で、1つの列車番号に複数の列車は0件）。

### 7.3 データの作り直し

- 今回の JSON は一時スクリプト（リポジトリに入れていない）で作った。手順は次のとおり。
  1. `node_modules/.cache/unyohub/timetable.json` の honsen を読み、`next_trains` / `previous_trains` で空港線・和歌山港線をつなぐ。加太線はつながず、行先を「加太線直通」とした。回送は除いた。
  2. 種別の対応: 普通 → local、急行 → express、空港急行 → airport、サザン → southern、ラピートβ → limited。ラピートα・区急・準急・`-急行-` は対応なし。
  3. コースの駅に時刻がある（2駅以上）列車を、コースごとに集めた。
  4. 抜かれは 2.1 の方法。
  5. ゲーム側は ROUTES に applyService を時間帯ごとに当てて読んだ。
- 改正があれば、Hub のキャッシュを取り直し（`npm run oncoming:meets -- --timetable --refresh`）、同じ手順で作り直す。
